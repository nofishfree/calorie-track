### 2.4 数据流向

```
登录流程:
  用户提交 email + password
    → POST /api/auth/login
    → 后端验证 (email + bcrypt 密码匹配)
    → 返回 { token, user }
    → 前端存储 token + user 到 authStore (localStorage 持久化)
    → 启动轮询同步 (startPolling)

自动登录:
  App.tsx → AutoLogin 组件
    → 从 localStorage 读取 auth-storage
    → 调用 login(token, user) 恢复状态
    → 若为远程账号则启动轮询

登出流程:
  logout()
    → 调用 stopPolling() 停止同步
    → 清除 token，切换到 local-account
    → 从 savedAccounts 中移除当前账号
```

## 三、头像 (Avatar) 模块

### 3.1 设计背景

头像数据使用单独的表存储，通过 SHA-256 哈希值索引。原因：
1. **减少请求体大小**：操作队列中只存储哈希值（64 字符），而非完整的 base64 数据（可能 6.7MB+）
2. **去重**：多个用户使用相同头像时，数据库只存储一份
3. **离线支持**：头像数据在本地 IndexedDB 缓存，无网络时仍可显示

### 3.2 前端数据结构

#### LocalAvatar (IndexedDB 存储结构)
```typescript
interface LocalAvatar {
  hash: string           // SHA-256 哈希值（64位十六进制）
  data: string           // base64 编码的头像数据
  created_at: number     // 创建时间戳
}
```

#### avatarStore 方法
```typescript
// 并发检查头像哈希是否在数据库中，不在则上传（非阻塞，不影响接口）
// 仅在已登录且非本地账号时执行；使用 uploadingHashes Set 去重避免重复上传
syncAvatarToServer(hash: string, data: string): Promise<void>

// 保存头像到本地 IndexedDB（写入时机：并发触发 syncAvatarToServer）
saveAvatar(hash: string, data: string): Promise<void>

// 从本地 IndexedDB 获取头像数据（查询时机：查到数据时并发触发 syncAvatarToServer）
getAvatar(hash: string): Promise<string | null>

// 检查本地是否存在头像
hasAvatar(hash: string): Promise<boolean>

// 从服务器获取头像并保存到本地（修改时机：先 checkAvatar 检查存在再 getAvatar，避免 404）
fetchAvatarFromServer(hash: string): Promise<string | null>

// 获取头像数据（优先本地，不存在则从服务器获取）
getOrFetchAvatar(hash: string): Promise<string | null>

// 删除本地头像
deleteAvatar(hash: string): Promise<void>

// 计算字符串的 SHA-256 哈希值
computeHash(data: string): Promise<string>
```

### 3.3 后端数据结构

#### Avatar (数据库模型)
```rust
pub struct Avatar {
    pub id: Uuid,
    pub hash: String,           // SHA-256 哈希值（64位十六进制）
    pub data: String,           // base64 编码的头像数据
    pub created_at: DateTime<Utc>,
}
```

#### UploadAvatarRequest
```rust
pub struct UploadAvatarRequest {
    pub hash: String,           // SHA-256 哈希值
    pub data: String,           // base64 编码的头像数据
}
```

### 3.4 数据流向

```
上传头像流程（并发同步）:
  用户选择图片 → FileReader 读取为 base64
    → computeHash(base64Data) 计算 SHA-256 哈希值
    → avatarStore.saveAvatar(hash, base64Data) 存储到 IndexedDB
      → 并发触发 syncAvatarToServer(hash, data)
        → 调用 checkAvatar(hash) 检查服务器是否已存在
        → 若不存在 → 调用 uploadAvatar({ hash, data }) 上传
        → 使用 uploadingHashes Set 去重，避免重复上传
    → 更新 user.avatar = hash
    → 添加操作到队列: { entity_type: 'account', data: { avatar: hash } }

显示头像流程:
  组件接收 user.avatar (哈希值)
    → avatarStore.getAvatar(hash) 尝试从 IndexedDB 获取
      → 查到数据时并发触发 syncAvatarToServer (确保服务器也有)
    → 若本地不存在 → getOrFetchAvatar(hash)
      → fetchAvatarFromServer(hash)
        → 先 checkAvatar(hash) 检查服务器是否存在 (避免 404)
        → 若存在 → getAvatar(hash) 获取数据 → saveAvatar 存到本地
        → 若不存在 → 返回 null
    → 返回 base64 数据 → 显示图片
    → 若无数据 → 显示默认头像图标
```

### 3.5 头像同步触发时机

| 时机 | 触发方法 | 行为 |
|------|---------|------|
| 写入 | `saveAvatar()` | 本地写入后并发触发 `syncAvatarToServer` |
| 查询 | `getAvatar()` | 查询到数据后并发触发 `syncAvatarToServer` |
| 修改 | `fetchAvatarFromServer()` | 从服务器获取后通过 `saveAvatar` 间接触发 |

`syncAvatarToServer` 流程：检查哈希是否在数据库 → 不在则上传，全程非阻塞、并发执行。

## 三、食物 (Food) 模块

### 3.1 前端数据结构

#### Food (前端类型 — 完整结构)
```typescript
interface Food {
  id: string              // UUID，前端生成
  name: string            // 食物名称
  num: number             // 每份量基准数量（如 100g）
  calorie: number         // 每份量热量
  calorie_unit: 'kcal' | 'kj'  // 热量单位
  carbs_g: number         // 每份量碳水（克）
  protein_g: number       // 每份量蛋白质（克）
  fat_g: number           // 每份量脂肪（克）
  unit: string            // 份量单位（如 'g', 'ml', '个'）
  user_id?: string        // 所属用户 ID（可选，系统食物为 undefined）
}
```

#### ServerFood (服务器食物响应)
```typescript
interface ServerFood {
  id: string
  user_id: string | null   // 服务器返回 null 表示系统食物
  name: string
  num: number
  calorie: number
  calorie_unit: string
  carbs_g: number
  protein_g: number
  fat_g: number
  unit: string
  usage_count?: number | null
}
```

**映射关系**: `ServerFood.user_id (string | null)` → `Food.user_id (string | undefined)`

#### FoodState (食物状态)
```typescript
interface FoodState {

  lastUsedServings: Record<string, number>   // 上次使用份量，key: `${foodId}:${userId}`
  savedFoodIds: Record<string, string[]>     // 各账号保存的食物 ID 列表
  newlyCreatedFoodIds: string[]              // 新创建的食物 ID（未持久化）
  modifiedFoodIds: string[]                  // 已修改的食物 ID
```

### 3.4 数据流向

```
创建食物:
  用户填写表单 → generateUUID() 生成 ID
    → foodsAPI.createFood({ id, name, ... })
    → 后端验证 ID 格式 → 插入 foods 表 → 记录操作日志
    → 前端: foodStore.addFood(food)
      → 更新 foods[] 列表
      → 调用 operationStore.addOperation('food', data)  // data.id 即实体ID
        → 操作进入待同步队列
    → 版本化同步时通过 versionedSync 接口上传
      → 后端异步 execute_operation() 写入 foods 表 + 记录日志

更新食物（跨用户）:
  若原食物属于其他用户 → 生成新 ID → 作为新食物添加
  若属于当前用户 → 原地更新 → 添加 'update' 操作到队列

加载食物列表:
  登录后 → foodsAPI.getFoods()
    → 返回 ServerFood[] → 映射为 Food[]
    → foodStore.setFoods(foods) 覆盖本地数据
    → 本地操作队列优先于服务器数据
```

### 4.4 数据流向

```
添加记录:
  用户选择食物 → 设置份量 → 计算营养
    → recordStore.addRecord({...})
      → 生成 UUID 作为记录 ID
      → records[] 新增记录（Zustand 内存）
      → operationStore.addOperation('record', data)  // 入同步队列，data.id 即实体ID
      → IndexedDB 异步保存 (queueMicrotask)
      → 版本化同步时通过 versionedSync 接口上传
        → 后端异步 execute_operation() 写入 meal_records 表 + 记录日志

每日营养统计:
  getDailyNutrition(date)
    → 过滤当天记录 → reduce 求和
    → 返回 { calories, protein, carbs, fat }

服务器加载记录:
  recordsAPI.getRecordsByDate(date)
    → 返回 ServerMealRecord[]
    → 前端映射为 MealRecord[]
    → recordStore.setRecordsForDate(date, records)
```

### 7.2 OperationItem (操作队列项)
```typescript
interface OperationItem {
  id: string                                    // 操作唯一 ID (UUID v4，crypto.randomUUID() 生成)
  operation_type: 'add' | 'update' | 'delete'
  entity_type: 'food' | 'record' | 'plan' | 'goal' | 'account'
  data: any                                      // 实体完整数据 (data.id 即为实体 UUID)
  created_at: string                             // ISO 8601
}
```

> **注意**: 
> - 操作 `id` 使用 UUID v4 格式（`crypto.randomUUID()`），符合 PostgreSQL UUID 格式和全局唯一性约束。
> - 实体 ID 统一通过 `data.id` 获取，不再使用独立的 `entity_id` 字段。
> - `SyncOperationRequest` 中的 `id` 字段即操作唯一 ID，用于后端去重和写入 `operation_logs.id`。

队列按用户 ID 分组存储: `Record<userId, OperationItem[]>`

### 7.3 同步请求/响应

#### VersionedSyncRequest (前端→后端)
```typescript
interface VersionedSyncRequest {

  head_operation?: SyncOperationRequest | null  // 队头操作
}

interface SyncOperationRequest {
  id: string                            // 操作唯一 ID (UUID v4，前端生成，用于去重和写入 operation_logs.id)

```

#### VersionedSyncResponse (后端→前端)
```typescript
interface VersionedSyncResponse {
  server_version: number               // 服务器当前版本 (max serial_number)

  head_processed: boolean               // 队头操作是否已处理
}

interface OperationLog {
  id: string
  user_id: string
  serial_number: number                // 操作序号（自增）
  operation_type: string
  entity_type: string
  data: Record<string, unknown>        // data.id 即为实体 UUID
  created_at: string
}
```

### 7.4 后端同步处理逻辑

```
versioned_sync() (同步响应，即时返回):
  1. 获取服务器数据版本 (MAX(serial_number) FROM operation_logs)
  2. 处理队头操作:
     a. 使用 head_op.id 查询 operation_logs (WHERE user_id = $1 AND id = $2)
     b. 若已存在 → 标记 head_processed = true (前端可移除该操作)
     c. 若不存在 → 加入内存操作队列
     d. 启动异步任务 (tokio::spawn) 处理队列
     e. 返回 head_processed = false (前端保留该操作)
  3. 若 server_version > client_version
     → 返回 serial_number > client_version 的增量操作日志
  4. 立即返回 VersionedSyncResponse

异步任务 (后台执行，不阻塞前端):
  process_operation_queue():
    1. 从内存队列取出所有操作
    2. 获取当前最大序列号，计算 next_serial
    3. 开启数据库事务
    4. 对每个操作:
       a. execute_operation() 写入业务表
          - food → INSERT/UPDATE/DELETE foods 表
          - record → INSERT/UPDATE/DELETE meal_records 表
          - plan → INSERT/UPDATE/DELETE meal_plans + plan_items 表
          - goal → INSERT/UPDATE/DELETE goal_templates 表
          - account → UPDATE users 表
       b. 写入 operation_logs (使用前端提供的 op.id 作为主键，保证幂等性)
    5. 提交事务

execute_operation() (业务操作分发):
  • 根据 entity_type 和 operation_type 组合执行对应 SQL
  • 所有操作在同一事务中，保证数据一致性

幂等性保证:
  • 同一操作无论被重发多少次，后端通过 id 精确识别
  • operation_logs.id 使用前端生成的 UUID，INSERT 时若已存在则报错跳过
  • 前端通过 head_processed 判断是否可安全移除队列中的操作
```

### 7.5 数据库表: `operation_logs`
| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID (PK) | 主键（前端生成的操作 UUID v4，用于去重） |
| user_id | UUID (FK→users.id) | 用户 ID |
| serial_number | BIGINT | 序列号（版本号），与 user_id 联合唯一 |
| operation_type | VARCHAR(20) | 操作类型: add/update/delete |
| entity_type | VARCHAR(20) | 实体类型: food/record/plan/goal/account |
| data | JSONB | 操作数据快照 (data.id 即为实体 UUID) |
| created_at | TIMESTAMPTZ | 创建时间 |

### 7.6 后端 execute_operation 操作映射

后端通过 `execute_operation()` 函数根据 `entity_type` 和 `operation_type` 组合执行对应 SQL：

| entity_type | operation_type | 目标表 | 操作 |
|-------------|---------------|--------|------|
| food | add | foods | INSERT |
| food | update | foods | UPDATE (COALESCE 部分更新) |
| food | delete | foods | DELETE |
| record | add | meal_records | INSERT |
| record | update | meal_records | UPDATE (COALESCE 部分更新) |
| record | delete | meal_records | DELETE |
| plan | add | meal_plans + plan_items | INSERT (事务内) |
| plan | update | meal_plans + plan_items | UPDATE + 重新插入 items |
| plan | delete | plan_items + meal_plans | DELETE (先子后父) |
| goal | add | goal_templates | INSERT |
| goal | update | goal_templates | UPDATE (COALESCE 部分更新) |
| goal | delete | goal_templates | DELETE |
| account | update | users | UPDATE (username, avatar_hash) |

**注意**:
- 所有操作在同一数据库事务中执行，保证数据一致性
- plan 类型操作涉及两张表 (meal_plans, plan_items)，使用事务保证原子性
- goal update 操作会先将其他模板的 is_current 设为 FALSE

### 7.7 同步触发时机

| 时机 | 触发方式 |
|------|---------|
| 登录成功后 | `startPolling()` 启动每秒轮询 |
| 自动登录后 | `AutoLogin` 组件检测到远程账号 → `startPolling()` |
| 登出时 | `stopPolling()` 停止轮询 |
| 后台运行 | 定时器 `setInterval` 每 1000ms 调用 `performSync()` |
